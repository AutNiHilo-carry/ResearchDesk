# 技术选型 v1 开发侧审查

审查日期：2026-11-16。审查者：开发助手。此记录不是独立人工审核，也不改变候选 rubric、默认策略或已有结果。

## 资料核对

核对了来源清单中5个官方页面。SQLite 的单写者、WAL 同机限制与本地应用场景，以及 PostgreSQL 18 的 MVCC 与冲突行锁机制，可用于这组短资料任务。参考 [SQLite WAL](https://www.sqlite.org/wal.html)、[隔离](https://www.sqlite.org/isolation.html)、[使用场景](https://www.sqlite.org/whentouse.html)、[PostgreSQL 18 MVCC](https://www.postgresql.org/docs/18/mvcc-intro.html)、[显式锁](https://www.postgresql.org/docs/18/explicit-locking.html)。

摘记包含项目编写的解释、范围限制和“没有外部 exactly-once 协议”等局部资料声明。它们不是官方网站对所有产品能力的否定。哈希清单只绑定本地摘记，不能验证解释一定正确。

## 发现与处理

- 摘记直接包含若干待检验推论，问题也明确提醒主要限制。任务偏容易，存在答案线索，适合作为基础流程试验，不作为独立留出集或复杂推理能力证明。本轮保留 v1 字节与哈希，不在看到结果后改题或改 rubric。
- `shared_network_wal` 的替代方案标准使用“可建议”，解释余地较大。人工复核时应区分拓扑判断与可选建议，不能仅凭评分器输出宣称该标准已校准。
- 200字正文约束只适合短回答，不能代表完整技术选型报告。8题未覆盖实际检索、负载测试、冲突资料与更长任务。
- 通用摘要之前将所有资料硬编码为“虚构资料”。现改为展示实际 scope 和候选标签状态；缺失值显示 unspecified，不推断来源性质。
- 生成请求仅含题目与附带资料，不包含 criteria；评分请求包含 criteria。这只能防止直接传入评分表，不能消除摘记或题目自身的答案线索。

## 首轮试验合同

选择现有任务集前3题：`local_low_write`、`shared_network_wal`、`wal_single_writer`。固定顺序 v1→v2，使用 deepseek-flash，每题每组最多6次生成请求，另每组最多2次批量评分；总上限40次 SDK 请求，无搜索、无自动重试。它是请求上限，不是 Token 或金额上限。

资料、提示词、代码、预算以执行前新建冻结计划为准。发送给 DeepSeek 的只有公开官方资料的项目摘记、自编题目、rubric 及生成报告。运行产物保留在忽略的 runs 目录，不发布凭证或原始调用日志。失败和未知结果保留，不重跑覆盖，不自动晋升。

同模型生成和评分、固定顺序、单次重复与已用于开发的任务集都构成偏差。首轮结果只描述3题的观察；独立人工审核仍 pending。下一版难度提升应另建任务集，采用更少结论提示的原始资料片段与未用于开发的新任务。
